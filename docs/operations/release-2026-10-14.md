# Release: 2026-10-14

## Included

- Tasks retain the list structure when empty. Tasks and tickets share assignment
  rules and one Associated Objects field in their configurable creation forms.
- Invitation acceptance receipts, private administrator DPA, and public legal links.
- Organization owners can start/cancel closure for their own organization; the
  CRM owner can do so across organizations. Other administrators cannot.
- Closure immediately freezes tenant writes, incoming forms and background
  integrations. Existing read/export permissions remain for 30 days.
- Cancellation before the deadline preserves records. After the deadline there
  is no reactivation; scheduled deletion removes active organization data.
  Shared user accounts and other organizations are preserved. A minimal deletion
  ledger and file-cleanup retries survive the tenant deletion.

## Manual Render deployment

Use the same main-branch commit for all four services:

1. API (`hdm-crm-staging-api`): run `sh bin/release.sh` as the Pre-Deploy Command.
   This applies migrations `0078_legal_acceptance` and `0079_organization_lifecycle`.
   Wait for a successful Live deployment before deploying the other services.
2. Worker (`hdm-crm-staging-worker`).
3. Scheduler (`hdm-crm-staging-scheduler`); keep exactly one scheduler instance.
4. Web (`hdm-crm-staging-web`).

In the shared backend environment group, use `CRM_ORG_CLOSURE_ENABLED=true` and
`CRM_ORG_PURGE_ENABLED=true`. Both now default to true, but old explicit service
overrides set to false take precedence and must be corrected. No database or
Redis service redeploy is required. Do not run release migrations simultaneously
on workers. If API has no Pre-Deploy Command, use its Shell to run the release
command before proceeding with Worker, Scheduler and Web.

The scheduler checks overdue closures once daily at 04:00 UTC. Access ends at the
30-day deadline; deletion follows at the next daily run (up to 24 hours later,
subject to worker availability and retries). Other scheduled jobs keep their
existing frequencies. Worker errors are logged and retried; storage cleanup runs
separately. Disabling purge is an emergency
pause only, and never restores access or extends the 30-day deadline. Monitor
`Organization purge failed` messages and overdue uncompleted deletion receipts.

`CRM_LEGAL_VERSION` remains empty by default, independently of organization
closure: deploying this release alone does not enforce legal acceptance. The
private DPA still carries its review status. Activate versioned acceptance only
with the matching final document version.

## Website delivery

The Hostinger ZIP is separate from this repository. Extract its contents directly
inside `public_html`, with `index.html` at that level. Preserve existing `.htaccess`
and `.well-known` files. If previously uploaded, remove these obsolete public files:
`crm-dpa.html`, `crm-dpa-es.html`, `crm-providers.html`, `crm-providers-es.html`.
The private DPA is served by the authenticated CRM, not by Hostinger.

The Google Tag Manager confirmed-quote trigger draft is a separate publishing
step; committing this repository or uploading the website does not publish GTM.
